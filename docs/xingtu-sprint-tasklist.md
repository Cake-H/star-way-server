## M1 · 商业化底座（P0，不做不能上线）

### 1.1 AI 额度与用量计量 ★最高优先级

**背景**：当前 LLM 调用（DeepSeek，4 个 Assistant）只配了 maxTokens 上限，**完全不记录用量**，放量即亏损。

- [ ] **DB：新增 `database/mysql/ida_v5_billing.sql`**
  - `ida_user` 扩展字段：`balance`(额度余额)、`total_quota`(累计额度)、`member_level`(会员等级，预留)
  - `ida_ai_usage_record`：id、user_id、biz_type(resume_parse/autofill/interview_summary/mock_interview/...)、biz_id、model、prompt_tokens、completion_tokens、cost_quota、create_time
  - `ida_quota_transaction`：额度流水（充值/扣减/赠送/每日免费发放），type、amount、balance_after、remark
- [ ] **计量组件（ida-ai 模块）**：LangChain4j ChatModel 监听器/AOP 切面，统一拦截 4 个 Assistant 调用，从响应中读取 token usage 落库
- [ ] **额度守卫**：所有 AI 接口入口前置校验（余额不足返回明确错误码 + 引导充值文案）；扣减与业务调用同事务/失败补偿策略
- [ ] **每日免费额度**：定时任务每日发放（如 10 点），保活跃、控成本
- [ ] **错误码**：ida-common 新增 `QUOTA_INSUFFICIENT` 等错误码
- [ ] 验收：构造余额=0 用户，4 条 AI 链路全部被拦截且提示正确；每次调用用量表有准确记录

### 1.2 充值（测试期过渡方案）

- [ ] **兑换码机制**：`ida_redeem_code` 表（code、quota、status、used_by、expire_time）；后台生成 → 用户端"兑换额度"入口
- [ ] 用户端接口：查询余额、查询额度流水、兑换码充值
- [ ] （M4 再做）微信/支付宝支付、订单表、支付回调
- [ ] 验收：测试期无需支付通道即可给种子用户发额度

### 1.3 最小管理后台

**原则：不建独立 admin 模块**，在 ida-app-server 加 `/admin/**` 接口组 + 管理员角色标记 + 简单前端页（或先用 Apifox 操作）。

- [ ] 管理员鉴权：`ida_user` 加 `role` 字段（user/admin），拦截器校验
- [ ] 接口：用户列表/详情、用户用量看板（按人/按业务/按天聚合）、手动调整额度、兑换码生成/列表、站点模板管理（见 2.1）
- [ ] 验收：管理员能看到"哪个用户、哪天、哪个功能、烧了多少 token"，可手动加额度

### 1.4 隐私安全基线

简历含姓名/电话/学历/公司等敏感信息，属合规红线。

- [ ] **AI 请求脱敏**：推广 `FeedbackConsumerMask`（ida-plugin 已有雏形）到全部 4 条 LLM 链路，手机号/身份证/邮箱入 prompt 前打码
- [ ] **存储加密**：简历手机号等敏感字段 AES 加密落库（MyBatis TypeHandler 透明加解密）
- [ ] **传输与权限**：确认全站 HTTPS；简历/OSS 文件访问必须带鉴权签名 URL，禁止公开读
- [ ] **隐私协议 + 用户协议**页面（前端），注册勾选
- [ ] **账号注销 + 数据删除**接口（合规要求）
- [ ] 验收：抓包确认 LLM 请求无明文手机号；OSS 直链无法匿名访问

## M2 · 核心链路做精（P0/P1）

### 2.1 插件站点模板扩容：1 → ≥10 个 ★差异化卖点

**背景**：一键填表是最成熟、最有壁垒的模块，但目前只有 `site-templates/beisen.json` 1 个模板，卖点成色不足。

- [ ] 梳理目标站点清单（按秋招覆盖率排序）：北森(已有)、Moka、智联招聘、前程无忧、实习僧、BOSS直聘网页版、牛客、各大厂自建校招系统（腾讯/阿里/字节/美团/京东等选 Top5）
- [ ] 每个站点：调研表单 DOM 结构 → 编写 site-template JSON → 录入 `SiteTemplateRegistry` → 实测填充
- [ ] **可用 Agent 批量并行**：每个站点模板是独立 JSON + 独立验证，适合一个站点一个子任务
- [ ] 每模板配套单测（参照已有 `SiteTemplateMatcher/Registry` 测试模式）
- [ ] 管理后台提供模板上下架开关（复用 1.3）
- [ ] 验收：Top10 站点一键填充字段命中率 ≥85%，逐字段 feedback 正常回传

### 2.2 模拟面试补测试与联调

**背景**：后端刚完成（commit `7082367`），零测试，不能带病进测试期。

- [ ] 单元测试：`MockInterviewGenerateAiService`（mock ChatModel）、场次/进度状态机（GENERATED→PRACTICING→COMPLETED 流转边界）
- [ ] 接口测试：按 `docs/mock-interview-apifox-testcases.json` 全量跑通
- [ ] 与前端联调（前端在另一仓库，**提前对齐排期**）
- [ ] 验收：核心链路测试覆盖，Apifox 用例全绿

### 2.3 已有链路体验优化（按优先级，够用即止）

- [ ] 简历 AI 解析失败重试 + 解析结果人工修正引导
- [ ] 面试复盘 voice-summarize：ASR 失败兜底（阿里云 NLS ↔ Whisper 切换降级）
- [ ] 全局：AI 接口超时/限流策略（Resilience4j 或简单重试），额度扣减失败回滚
- [ ] 验收：弱网/AI 服务异常场景下用户得到明确提示而非白屏/500

## M3 · 新功能补位（P1，严格只做这 2.5 个）

### 3.1 简历评估 + AI 优化建议 ★付费点

**理由**：简历域模型 + AI 链路现成，边际成本最低；竞品标配付费功能；与投递闭环叙事衔接。

- [ ] **DB：`ida_v6_resume_eval.sql`**：`ida_resume_evaluation`（resume_id、target_job、score、维度评分明细 JSON、建议明细 JSON、create_time）
- [ ] 新增第 5 个 Assistant：输入简历结构化数据 + 目标岗位 JD → 输出总分 + 分维度评分（关键词匹配/量化成果/结构规范）+ 逐条修改建议
- [ ] 接口：POST 评估（消耗额度）、GET 历史评估记录
- [ ] **"直接改写简历"作为高额度消耗的高级功能**（P2，测试期可后置）
- [ ] 前端：评估报告页（雷达图/分数 + 建议列表）
- [ ] 验收：上传简历+JD 后 30s 内出报告；扣额度正确；建议内容可落地（非套话）

### 3.2 网申网站列表

**理由**：纯配置型功能，1-2 天工作量，感知价值高，给插件引流。

- [ ] **DB**：`ida_apply_site`（名称、logo、url、分类(国企/互联网/银行/快消...)、是否支持插件一键填、排序、状态）
- [ ] 接口：分类列表查询（只读，无需后台先行可硬编码初始化 SQL）
- [ ] 前端：分类导航页，标记"支持一键投递"的站点引导装插件
- [ ] 验收：≥50 个站点入库，分类可筛选，跳转正确

### 3.3 轻量引导式简历制作（阉割版，控制 scope）

**明确不做**：可视化拖拽编辑器（秋招后再议）。
**做**：问答引导 → AI 生成 → 落入现有简历模型 → 固定模板导出。

- [ ] 引导流程：3-5 步问卷（基本信息/教育/经历/技能/求职意向），每步给 AI 示例话术
- [ ] 复用简历域：生成内容直接写入 `ida_resume` + 子表（不建新模型）
- [ ] 导出：2-3 套固定 HTML→PDF 模板（如 flying-saucer / freemarker + openhtmltopdf）
- [ ] 零经历用户兜底：AI 把课程/社团经历按 STAR 法则改写（prompt 工程，复用 3.1 Assistant）
- [ ] 验收：零基础用户 10 分钟内产出可导出 PDF 简历

## 跨模块通用要求

| 项 | 要求 |
|---|---|
| 新 DB 变更 | 一律新增 `database/mysql/ida_vN_xxx.sql`，不改历史脚本 |
| 错误码 | 统一放 ida-common，前端可解析 |
| 测试 | 新 AI 链路参照 ida-plugin 已有模式补单测；接口配 Apifox 用例文档（对齐 docs/ 现有风格） |
| 文档 | 每个新功能产出前端对接文档 + Swagger/Apifox 用例（对齐 docs/ 现有 12 篇风格） |
| 前端协同 | 前端在独立仓库，**每周对齐联调排期**，接口变更提前通知 |

## 风险清单

1. **前端进度是最大瓶颈**：后端任务再多，8-20 能否测试取决于前端联调，建议前端同步排期
2. **支付对接不可控**：测试期先用兑换码，不让支付阻塞节点
3. **站点模板调研成本不确定**：M2 预留 buffer，达不到 10 个时优先保证 Top6
4. **AI 成本**：测试期设每日免费额度上限 + 单用户日调用上限双保险
