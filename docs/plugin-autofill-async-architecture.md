# 插件端「一键填表」异步机制说明（新手向 · 由浅入深）

> 目标读者：第一次接触「异步、线程池、轮询」的同学。  
> 读完后你应该能用自己的话说明：**为什么**要异步、**和同步差在哪**、**扩展要怎么调接口**、**以后上线要注意什么**。

---

## 〇、先用一个生活比喻（不用记任何英文）

想象你去**网红奶茶店**买一杯要现做的饮料：

| 做法 | 像什么 | 你的感受 |
|------|--------|----------|
| **同步** | 店员接单后，**站在你面前**从泡茶、切水果一直做到封杯，**做完才把杯子给你**。你这段时间**一直占着柜台**，后面的人也要等。 | 等得久；你手机若设了「等太久就放弃」，可能**没拿到饮料就走了**（超时）。 |
| **我们做的异步 + 轮询** | 店员给你一张**取餐号**（`taskId`），你先走开；厨房**另一批人**慢慢做。你每隔一会儿**回来看电子屏**：「做好了吗？」直到显示「请取餐」或「失败」。 | 你**不用一直堵在柜台**；但每次去看屏，就是一次**很短的问话**（一次 HTTP），不容易超时。 |

对应到程序里：

- **柜台店员** ≈ 处理你浏览器请求的 **Web 服务器里的一条线程**（下面术语表里叫 **Tomcat 工作线程**）。  
- **厨房** ≈ 我们单独开的 **线程池**（名字里带 `plugin-autofill-` 的线程），在里面慢慢调大模型。  
- **取餐号** ≈ **`taskId`**。  
- **你反复看电子屏** ≈ **轮询**：多次 `GET`，每次只问「好了没」。

**重要一句**：异步**不会**让大模型算得更快；只是让你**不用在同一条 HTTP 连接上干等几分钟**，并且能**假装有个进度条**（其实是几个粗阶段）。

## 一、术语小词典（后面出现陌生词可以翻回来查）

> 说明：**专业术语** | **白话** | **小例子或类比**

| 术语 | 白话 | 小例子 |
|------|------|--------|
| **HTTP / 接口** | 浏览器和服务器之间「问—答」的一次对话 | `POST .../tasks` 问：「帮我排个队」；服务器答：「好，号码是 abc-123」 |
| **Tomcat 工作线程** | Web 程序里**专门处理某个 HTTP 请求**的工人 | 你点「提交」，服务器派一个工人接待你；工人处理完这个请求才能去接待别人 |
| **阻塞** | 工人**必须干等**某件事做完，才能往下走 | 工人站在那等大模型 API 回话 60 秒，这 60 秒这条线程**啥别的活也干不了**（对这条请求而言） |
| **同步接口** | **一条 HTTP** 从发起到拿到**最终结果**才结束 | 老接口 `POST .../autofill-plan`：连接一直开着直到填表计划算完 |
| **异步（我们这里特指）** | **先**用一条很快的 HTTP 拿到「号码」，**真正费时的活**交给**别的线程**慢慢做 | `POST .../tasks` 很快返回 `taskId`；算计划在别人那跑 |
| **线程池** | 预先养了一群工人，**排队领活干**，不用每来一个活就现招一个人 | `pluginAutofillExecutor`：里面几条线程专门跑填表任务 |
| **Runnable / execute** | 「**待办事项纸条**」和「**把纸条扔进待办箱**」 | `execute(() -> runTask(...))`：把「跑填表」扔进池子；**扔完就返回**，不站在池子边等做完 |
| **轮询** | **隔一会儿问一次**「好了吗」，而不是一直连着电话不听筒 | 每 1 秒 `GET .../tasks/{taskId}`，直到状态变成成功或失败 |
| **DTO / VO** | 约定好字段名字的 **JSON 数据形状**，方便前后端对齐 | `PluginAutofillTaskStatusVO` 里有 `status`、`percent`、`result` 等 |
| **JVM / 进程** | Java 程序跑起来后的**一个独立世界**；关掉程序，里面的内存全没了 | 任务存在内存 Map 里 → **重启服务** → 任务没了 |
| **Redis** | 另一种**独立**的存储服务，多个服务器可以**共看同一份**数据 | 两台插件服务器时，把任务状态写 Redis，**哪台**收到轮询都能查到 |
| **网关 / Nginx 504** | 站在最外面的保安，等太久觉得不对劲就**掐掉连接** | 同步请求等模型太久，保安以为出事了，断开 |
| **ClientAbortException** | **你先挂电话**，对方还在说话 | 扩展超时关了连接，服务端算完想写响应，发现线断了 |
| **SSE / 流式** | **一条长连接**，服务器可以**断断续续一直往外推字** | 像直播弹幕一条条出来；我们**当前没做**，是一次性拿整段 JSON |
| **回调（Callback）** | 「做到某一步时，**顺便帮我通知一下**」 | `onProgress(阶段, 说明, 百分比)`：填表逻辑每走一步，**喊一声**更新任务状态 |
| **ConcurrentHashMap** | 多人同时往里存/取小格子，**不会把表撕烂** | 多个任务并发更新不同 `taskId`，用这个装任务表更安全 |
| **synchronized** | **同一行记录**多人改时，**排队一个一个改**，避免「只改了一半就被别人读走」 | 更新 `phase` 和 `message` 时打包一起改完，再给别人读 |

## 二、同步接口：以前怎么做？哪里难受？

### 2.1 流程（老接口）

扩展调用：

```http
POST /api/v1/plugin/resume/autofill-plan
```

服务器在这条请求的**处理线程**里依次：

1. 检查参数、读简历、拼给大模型的文字  
2. **一直等着** 火山方舟把大模型结果返回（可能几十秒～几分钟）← **这里最耗时**  
3. 把结果解析成 JSON、做安全检查  
4. **同一条 HTTP 响应**里把完整结果一次性返回  

这叫 **同步**：你发一个请求，**连接一直占着**，直到**全部做完**。

### 2.2 常见难受点（用白话对应）

| 你看到的 | 背后常常是 |
|----------|------------|
| 扩展报错「超时」 | 扩展或浏览器设了「最多等 30 秒」，但模型要 90 秒 |
| 网页 504 | 前面的网关/代理等不及，把连接掐了 |
| 用户觉得「死机了」 | 没有任何「正在干什么」的提示 |
| 日志里连接被中止 | 用户关了页面或超时，服务器还在算，回头想写答案发现人走了 |

## 三、我们做的「异步 + 轮询」：按时间顺序走一遍

下面用 **A = 扩展**，**S = 服务器** 对话形式，配合上面的比喻。

### 3.1 第一次：`POST .../autofill-plan/tasks`（取号）

1. **A**：「我要填表，这是简历 id 和页面快照。」  
2. **S**（Tomcat 工人）：  
   - 生成随机 **`taskId`**（像取餐号）；  
   - 在**自己内存里的小本本**上记一行：这个号、哪个用户、当前状态「排队中 `PENDING`」；  
   - 把「真正算填表」这件事写成纸条，扔进 **线程池的待办箱**（`execute`）；  
   - **立刻**回复：**「你的号是 taskId，去那边屏幕查。」** 然后 Tomcat 工人**去接下一个客人**。  
3. **要点**：`execute` **不会**等纸条上的活干完；它只负责**排队**。所以这条 HTTP **很快结束**。

### 3.2 厨房线程：`runTask`（真正做菜）

1. 线程池里某个**厨房工人**领到纸条，开始干活。  
2. 把状态改成「正在做 `RUNNING`」。  
3. 调用**和同步接口同一套**的 `planAutofill(...)`，只是多了一个「**进度汇报员**」：每走一步就更新小本本上的 `phase`、`message`、`percent`，并打日志 `[autofill-task ...]`。  
4. 成功：小本本写上「完成 `SUCCEEDED`」，附上最终结果 `result`。  
5. 失败：写上「失败 `FAILED`」，附上**人能看懂的**错误说明。

**注意**：**大模型仍然很慢**；慢的是**厨房线程**，不是柜台 Tomcat 线程。

### 3.3 很多次：`GET .../autofill-plan/tasks/{taskId}`（看屏幕）

1. **A** 每隔 0.5～2 秒问一次：「号 xxx 好了吗？」（不要太快，否则服务器压力大）  
2. **S**（Tomcat 工人）：**只读小本本**，核对「是不是本人问的」，把当前一行抄成 JSON 返回。  
3. **A** 看到：  
   - 还在 `PENDING` / `RUNNING`：继续问；界面可以用 `message`、`percent` 假装进度条；  
   - `SUCCEEDED`：读 `result`，往网页表单里填；  
   - `FAILED`：把 `errorMessage` 给用户看。

## 四、和「流式输出」差在哪？（很多人这里会混）

| | **我们现在的做法** | **流式（例如 SSE）** |
|--|-------------------|---------------------|
| 像什么 | 取号 + **反复问**「好了吗」 | **一直连着电话**，对方**想到一句说一句** |
| HTTP | 很多次**短**请求 | 往往 **1 条很长**的连接 |
| 大模型结果 | 还是**等整段**生成完再解析 | 可以**边生成边显示**（若平台支持） |
| 难度 | 相对好做 | 客户端、服务端、大模型 API 都要配合 |

我们**没有**做流式；以后若要做「打字机效果」，要再改一层去对接方舟的流式 API。

## 五、接口与代码速览（想查类名时看这里）

### 5.1 扩展要调的两个新接口

| 方法 | 路径 | 一句话 |
|------|------|--------|
| `POST` | `/api/v1/plugin/resume/autofill-plan/tasks` | 取 `taskId`，**不等**算完 |
| `GET` | `/api/v1/plugin/resume/autofill-plan/tasks/{taskId}` | **问进度/拿结果** |

**老接口还在**：`POST .../autofill-plan` = 同步，一条请求等到底（兼容旧扩展）。

### 5.2 主要 Java 类（包名略写，全名见源码）

| 类 | 干什么 |
|----|--------|
| `PluginResumeController` | 把上面 URL 接到 Java 方法 |
| `PluginAutofillTaskService` | 取号、扔线程池、查状态 |
| `PluginAutofillTaskRegistry` | **内存里**那张「小本本」`taskId → 状态` |
| `PluginAutofillExecutorConfig` | 创建线程池 Bean |
| `PluginFormAutofillAiService` | 真正调大模型、解析、清洗（同步/异步**共用**） |
| `PluginAutofillProgressSink` | 「进度汇报员」接口；同步时用**空实现**假装没这个人 |

公共返回形状（`ida-common` 里）：`PluginAutofillTaskSubmitResultVO`、`PluginAutofillTaskStatusVO`、`PluginAutofillProgressPhase`。

## 六、好处、坏处、以后可以怎么升级

### 6.1 好处（白话）

- 提交那一下**很快**，不容易被浏览器/网关掐断。  
- 日志里能看到**卡在大模型还是卡在解析**，排错方便。  
- 老扩展不用改也能用同步接口。

### 6.2 坏处（一定要知道）

1. **服务一重启**，内存里的小本本没了 → 用户再轮询会说「任务没了」。  
2. **开两台服务器**（负载均衡）时：任务可能记在 A 机器，轮询却问到 B 机器 → **查不到**。  
3. 轮询太密会**刷爆**服务器，要节制。  
4. 线程池排队队伍太长可能**拒收**新任务（要监控）。  
5. 进度条只是**粗的几段**，不是「每个字出来都动一下」。

### 6.3 以后可以怎么升级（从易到难）

| 想法 | 说明 |
|------|------|
| 用 **Redis** 存任务 | 多台机器**共用小本本**，要配过期时间 TTL |
| 用 **数据库** 存任务 | 更正规，可查历史、做统计 |
| 真 **流式** | 对接方舟流式 API + SSE/WebSocket，开发量更大 |
| **消息队列** | 超高并发时把「纸条」先堆进 MQ，慢慢消费 |

## 七、上线要不要改？和 Redis 的关系

- **单机部署** `ida-plugin-server`：**不必**为这个功能单独装 Redis。  
- **多台机器 / K8s 多个副本**：**必须**把任务状态放到**大家都能访问的地方**（Redis 或数据库），否则轮询经常扑空。  
- 线程池队列大小、线程个数：访问量大了再在 `PluginAutofillExecutorConfig` 里调。

## 八、自己检查：读完后试着回答这三句

1. **异步**在我们项目里，主要是指：**哪条线程**还在等大模型？**哪条线程**已经去接待下一个 HTTP 了？  
2. **轮询**和 **SSE 流式** 差的一句话是：一个是**多次短问**，一个是**一条长连不断推**？  
3. **没用 Redis** 时，**重启**或**多实例**会出什么问题？

（答案要点：1）大模型在线程池线程等，Tomcat 线程很快返回。2）对。3）任务丢或查不到。）

## 九、技术向补充（给以后对照代码的同学）

### 9.1 同步 vs 异步（工程用语对照）

- **同步 `POST .../autofill-plan`**：`RestClient` 阻塞在 **Tomcat worker** 上。  
- **异步 `POST .../tasks` + 池内 `planAutofill`**：同样阻塞在 **`plugin-autofill-*` 线程**上，Tomcat **不**跟大模型死磕。

### 9.2 工具清单（与术语表对应）

- **Spring `ThreadPoolTaskExecutor`**：托管线程池、可配置队列与线程名。  
- **`ConcurrentHashMap` + `synchronized`（单条记录）**：任务表并发安全 + 读快照不撕裂。  
- **`PluginAutofillProgressSink`**：同步路径 `noop()`，异步路径挂到 `Registry`。

### 9.3 HTTP 与类调用链（速查）

```
POST .../autofill-plan/tasks
  → PluginResumeController.submitAutofillPlanTask
  → PluginAutofillTaskService.submitTask
  → PluginAutofillTaskRegistry.register
  → ThreadPoolTaskExecutor.execute(runTask)

GET .../autofill-plan/tasks/{taskId}
  → PluginResumeController.getAutofillPlanTask
  → PluginAutofillTaskService.getTaskStatus
  → PluginAutofillTaskRegistry.snapshotFor

（后台）runTask
  → PluginFormAutofillAiService.planAutofill(userId, req, sink)
  → ArkChatCompletionClient.chatCompletions(...)
  → sanitizePlan(...)
```

以仓库最新 Java 与 OpenAPI 为准。
